## 1. 제품 개요

### 한 줄 요약
바드림 팀이 **화면을 클릭하면 그 화면에 반영된 기획·요구사항과 사용된 컴포넌트를 바로 확인**할 수 있는, 프로젝트 중심의 웹 디자인 협업 툴. 피그마 화면을 연결하는 '허브'로 시작해서 캔버스 기능을 하나씩 붙여 피그마를 점진적으로 대체한다.

### 이름의 뜻 — Iris(이리스)
> **기획 · 디자인 · 개발을 잇는 무지개**

- **신화 속 이리스**: 그리스 신화에서 무지개의 여신이자, 신들의 세계와 인간의 세계를 오가며 소식을 전하는 **전령**이다. 무지개를 다리 삼아 두 세계를 잇는다.
- **무지개 = 색 = 디자인**: 'iris'는 그리스어로 무지개를 뜻한다. 오늘날 눈의 '홍채'와 꽃 '붓꽃'을 가리키는 말도 여기서 왔다. 색을 다루고, 보는 일(눈)을 돕는 디자인 툴의 정체성과 맞닿는다.
- **전령 = 연결**: 이리스가 신과 인간 사이에서 말을 전했듯, 이 툴은 **기획(요구사항)의 말을 화면에 전하고, 화면의 정보를 개발로 전한다.** 흩어진 문서와 화면 사이에 다리를 놓는 것이 이 제품의 핵심 기능이다.
- **레퍼런스와의 연결**: 토스의 'Deus'(라틴어로 '신')처럼, 바드림의 툴도 신화 속 존재에서 이름을 가져왔다.
- **표기**: 영문 `Iris`, 한글 `이리스`. 사내 호칭은 "이리스에 올려주세요", "이리스에서 확인해요".

### 해결하는 문제
- 기획 문서(노션·PDF·Word 등), 피그마 화면, 개발 스펙이 **흩어져 있어서** "이 화면에 기획서의 어떤 항목이 반영됐지?"를 확인하려면 여러 도구를 오가야 한다.
- 바드림은 **이미 완성된 기획 문서를 기반으로 화면을 자동 생성**하는 방식으로 일하고 있다. 그런데 결과 화면과 원본 요구사항 사이의 연결이 기록되지 않아서 **누락·불일치를 검수하기 어렵다.**
- 피그마는 범용 툴이라 "프로젝트 → 문서 → 요구사항 → 화면 → 컴포넌트"라는 바드림 고유의 구조를 담을 수 없다.
  - 토스가 프레이머에 플러그인으로 사내 기능을 붙이지 못해 Deus를 자체 개발한 것과 같은 이유다.

### 핵심 가치
| 기존(피그마 + 노션) | Iris |
|---|---|
| 화면과 기획서가 별도 도구 | 화면을 선택하면 우측에 **반영된 요구사항 · 관련 문서 · 사용 컴포넌트** |
| 요구사항이 반영됐는지 사람이 기억 | 요구사항마다 **반영됨 / 일부 반영 / 미반영** 상태가 화면에 연결되어 기록 |
| 컴포넌트가 어디서 쓰이는지 모름 | 컴포넌트 → **이 컴포넌트를 쓰는 화면 전체** 역추적 |
| 범용 기능만 사용 가능 | 바드림 전용 기능을 계속 추가 가능 (Deus의 '플러그인 레이어' 철학) |

**기획은 이 툴에서 "하는" 것이 아니라 "확인하는" 것이다.** 문서는 툴 안에서 직접 쓸 수도 있지만, 주된 흐름은 완료된 문서를 가져와 화면과 대조하는 것이다.

## 2. 사용자

### 주요 사용자
- **누구**: 바드림 사내 크로스팀 5~20명 (기획자 · 디자이너 · 개발자)
- **상황**: 기획 완료 → 화면 제작(자동화/피그마) → 검수 → 개발 핸드오프 과정 전반
- **목표**
  - 기획자: 내 요구사항이 어느 화면에 어떻게 반영됐는지 확인
  - 디자이너: 화면을 만들면서 근거가 되는 기획 항목과 써야 할 컴포넌트를 바로 보기
  - 개발자: 화면에서 사용 컴포넌트·토큰·기획 의도를 한 번에 확인

### 사용자 시나리오
**시나리오 A — 기획 검수 (핵심)**
1. 기획자가 "착한구독 신청 플로우 개편" 프로젝트를 열고
2. 캔버스에서 `신청_02_요금제선택` 화면을 클릭하면
3. 우측 '기획' 탭에 이 화면에 연결된 요구사항 5개(반영 3 · 일부 1 · 미반영 1)가 뜨고, 미반영 항목을 누르면 원본 기획서의 해당 문단으로 이동해 하이라이트된다.

**시나리오 B — 문서 등록과 연결**
1. 기획자가 완료된 기획서 PDF를 업로드하면
2. 문서 안의 `REQ-001` 형식 항목이 요구사항 목록으로 자동 인식되고
3. 번호가 없는 문장은 드래그해서 "요구사항으로 만들기"를 누른 뒤 캔버스의 화면에 연결한다.

**시나리오 C — 개발 핸드오프**
1. 개발자가 화면을 선택하고 '개발' 탭을 열면
2. 사용 컴포넌트(`Button/Primary ×2 → <BdButton>`, `PriceCard ×3`)와 사용 토큰이 보이고
3. 컴포넌트를 누르면 같은 컴포넌트를 쓰는 다른 화면 목록이 뜬다.

**시나리오 D — 피그마 화면 가져오기**
1. 디자이너가 피그마 프레임 링크를 붙여넣으면
2. 썸네일과 레이어 정보가 저장되어 캔버스에 '화면'으로 놓이고
3. 레이어 이름에서 바드림 컴포넌트가 자동으로 집계된다.

## 4. 사용자 흐름 (User Flow)

### 핵심 흐름
```
로그인 → 프로젝트 홈 → 프로젝트 열기 → 문서 등록(작성/업로드/링크)
      → 요구사항 인식·지정 → 화면 추가(피그마 연결 or 직접 그리기)
      → 화면 ↔ 요구사항 연결 → 화면 클릭 → 인스펙터에서 반영 여부 확인
```

### 상세 흐름
1. **로그인**: 이메일 입력 → `@ba-dream.com`이 아니면 차단 → 메일로 온 6자리 코드 입력
2. **프로젝트 홈**: 최근 프로젝트 카드(썸네일·반영률·멤버) → 새 프로젝트 만들기
   - 목적별 시작 카드: 앱 화면 / 웹 화면 / 상세페이지. 디테일페이지스튜디오의 시작 카드 패턴을 차용했다.
3. **에디터 진입**: 좌측 Pages에서 페이지(플로우) 선택 → 캔버스에 화면들이 배치되어 있음
4. **문서 등록**: 좌측 'Docs' 탭 → `+ 문서` → 작성 / 업로드 / 링크 중 선택 → 읽기 뷰로 열림
5. **요구사항**: 읽기 뷰에서 자동 인식된 REQ가 하이라이트됨 → 번호가 없는 문장은 드래그해서 "요구사항으로 만들기"
6. **화면 추가**: 툴바 `화면` → 피그마 링크 붙여넣기 or 빈 프레임(기기 프리셋) 생성
7. **연결**: 두 가지 방법
   - 화면 선택 → 기획 탭 `+ 요구사항 연결` → 검색해서 선택
   - 문서의 요구사항을 캔버스 화면 위로 드래그
8. **확인**: 화면 클릭 → 반영 상태 변경, 메모 작성 → 프로젝트 홈의 반영률에 반영됨

## 5. 화면 구성 & 디자인 방향 (디자인 작업 입력값)

> **디자인 기준 (2026-11-22 확정)**: 바드림 디자인 시스템 `@ba-dream/design-system`의 컴포넌트·토큰·아이콘과 저장소 `docs/AUTO-MAKE.md` 규칙을 따르고, 무드는 [design-system.ba-dream.com](https://design-system.ba-dream.com)에 맞춘다. 시안: [design/iris-canvas](../design/iris-canvas/README.md)

### 레이아웃 원칙 (Figma + Deus)
- **구조**: 좌측 패널 / 중앙 캔버스 / 우측 패널. 피그마 사용자가 학습 없이 쓸 수 있게 한다.
- **룩앤필**: Deus 스타일.
  - 연회색 캔버스 위에 모서리가 둥근 **흰색 플로팅 패널**을 올리고, 경계선은 최소화한다.
  - 화면 위에 기기명 라벨, 선택하면 `375×812` 크기 배지를 띄운다.
- **툴바**: 캔버스 위에 떠 있는 **알약(pill) 모양**.
  - 도구: 이동 · 프레임/화면 · 사각형 · 텍스트 · 이미지 · 컴포넌트 · 요구사항 연결 · 코멘트(P2)
- **좌측 패널 탭**: `Pages` · `Layers` · `Assets(컴포넌트)` · `Docs(문서·요구사항)`
  - 레이어 트리에서 컴포넌트 인스턴스는 **색 + 다이아몬드 아이콘**으로 구분한다. Deus와 같은 방식이다.
- **우측 패널 탭**: `디자인`(속성) · `기획`(요구사항·문서) · `개발`(컴포넌트·토큰·치수)
  - 피그마의 Design / Dev Mode 구분을 바드림식으로 확장한 것이다.
- **속성 패널**: 원시값 대신 **시맨틱 토큰**을 우선 노출한다. 예: "본문 16 / Gray700 – 기본 텍스트"
- **문서 읽기 뷰**: 캔버스와 **분할 보기**(좌 캔버스 / 우 문서)
  - 문서의 요구사항을 클릭하면 연결된 화면이 캔버스에서 하이라이트된다.
  - 반대로 화면을 클릭하면 문서가 해당 문단으로 스크롤된다.
- **상태 색**: 반영됨(초록) · 일부 반영(주황) · 미반영(빨강/회색) · 해당없음(연회색)
- **글꼴**: Pretendard. **UI 문구**: 한국어 우선이고, 디자인 속성 라벨은 피그마 용어(W/H, Fill, Radius)를 유지한다.

### Phase 1 디자인 대상 화면
| # | 화면 | 핵심 요소 |

| 3 | 에디터 — 디자인 모드 | 좌 Pages/Layers, 캔버스(여러 화면), pill 툴바, 우 디자인 속성 |

## 7. 안 만드는 것 (Out of Scope — Phase 1)

> AI에게 코드를 시킬 때 이 목록을 함께 공유하세요.

- 실시간 동시편집·커서 표시 — 이유: 1주 안에 넣으면 다른 기능의 품질이 무너진다. Phase 3.
- 오토레이아웃·펜/벡터·불리언·마스크 — 이유: 캔버스 엔진의 난이도가 급격히 올라간다. Phase 2~3.
- 피그마 파일을 편집 가능한 레이어로 변환 — 이유: 변환 정확도 문제가 크다. Phase 1은 썸네일과 레이어 요약만 가져온다.
- 프로토타입·코드 생성 — 이유: Phase 3.
- AI 기능 전반 (요구사항 자동 추출, 화면 생성) — 이유: 비용과 검증 시간이 든다. Phase 2.
- 외부(협력사) 계정·공개 공유 링크·세밀한 권한 — 이유: 사내 전용이고, 모든 멤버가 편집 가능.
- 노션 비공개 페이지 연동 (Notion API) — 이유: 공개 링크·붙여넣기로 대체. Phase 2.
- 모바일 앱 / 모바일 편집 — 이유: 데스크톱 웹 전용 (1280px 이상). 모바일은 읽기만 깨지지 않으면 된다.
- 다크 모드 — 이유: Phase 2.

## 8. [NEEDS CLARIFICATION]

- [ ] **회사 메일 시스템**: `@ba-dream.com`이 구글 워크스페이스라면 "구글로 로그인(도메인 제한)"을 추가해 더 편하게 만들 수 있다.
- [ ] **피그마 플랜/토큰**: 팀 공용 피그마 Personal Access Token을 누구 계정으로 발급할지 정해야 한다. 피그마 플랜에 따라 API 호출 한도가 다르다.
- [ ] **요구사항 번호 규칙**: 현재 기획서에서 쓰는 형식을 확인해야 한다 (`REQ-001`? `FR-01`? 표 형식?). 자동 인식 규칙을 여기에 맞춘다.
- [ ] **한글(HWP) 문서**: 업로드 지원이 필요한지. 필요하면 Phase 2에서 변환 방식을 검토한다.
- [ ] **바드림 브랜드 컬러·로고**: 툴 자체의 포인트 컬러를 정해야 한다 (기본값: 중립 회색 + 블루 포인트).
- [ ] **기존 바드림 디자인 시스템 소스**: 컴포넌트 목록을 피그마 라이브러리에서 가져올지, 코드 저장소에서 가져올지, 수동으로 입력할지.
